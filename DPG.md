# RITU as a Digital Public Good

Assessed against the nine indicators of the [DPG Standard](https://digitalpublicgoods.net/standard/).

---

### 1. Relevance to Sustainable Development Goals

**SDG 2 (Zero Hunger)** and **SDG 13 (Climate Action)**.

RITU addresses a specific failure mode in smallholder agriculture: inherited sowing calendars that were correct for a previous climate and are no longer correct for the present one. Germination failure from mistimed sowing is a direct driver of crop loss, debt and food insecurity. The tool measures the shift and corrects the calendar against it.

### 2. Use of an approved open licence

**MIT**, in [`LICENSE`](LICENSE). All code, schemas and derived data files are covered.

Upstream data retains its own terms: IMD gridded rainfall (India Meteorological Department), Open-Meteo (CC-BY 4.0), Agmarknet via data.gov.in (Government Open Data Licence – India).

### 3. Clear ownership

Ownership is recorded in `LICENSE` and the repository metadata. No contributor licence agreement is required.

### 4. Platform independence

No proprietary dependency anywhere in the stack.

- Frontend: React, Vite, Tailwind — all MIT
- Data pipeline: Python standard library plus `numpy` and `scipy`
- Rainfall archives are **NetCDF-3**, read with `scipy.io` — no `netCDF4`, `xarray` or HDF5 binaries required
- No chart library; the charts are hand-written SVG
- No backend, no database, no cloud service. The build output is static files.

There is no vendor to be locked into. A state could fork this and run it on any static host.

### 5. Documentation

[`README.md`](README.md) documents the problem, the findings, the full method, the data sources, how to run it and how to regenerate every derived file.

The method is stated precisely enough to be reimplemented independently:

> Agricultural monsoon onset is the first day on or after 1 June where the next 7 days accumulate ≥ 25 mm, with no dry spell longer than 7 consecutive days (< 2.5 mm daily) in the following 30 days. Trend by Theil–Sen; significance by Mann–Kendall with tie correction.

### 6. Mechanism for extracting data

All data is **plain JSON in the repository**, not locked in a database:

| File | Contents |
|---|---|
| `src/data/districts.json` | onset series, trend, p-value, supporting metrics for 36 districts |
| `src/data/prices.json` | mandi prices by district and crop |
| `src/data/crops.js` | crop calendar, water need, soil effect |
| `src/data/soil.json` | Soil Health Card nutrient status, 34 districts, 3 cycles |
| `src/data/sellTiming.json` | holding record and seasonal price shape per district and crop |
| `data/raw/mandi_monthly.json` | 11 years of Agmarknet prices, as monthly medians per district and crop |
| `data/raw/imd_rainfall_maharashtra.json` | 41 years of daily rainfall, 36 districts |

Every derived file is regenerated by a script in [`scripts/`](scripts/). Nothing is hand-written, so any figure in the app can be traced to source and recomputed. Scheduled GitHub workflows rerun those same scripts, so the published data stays current without anyone touching it: mandi prices four times a day, satellite greenness weekly, Soil Health Card counts and sell timing monthly. Each refuses to replace good data with a thin or empty response.

### 7. Privacy and applicable laws

**No personal data leaves the device.** The farmer's name, village, district and landholding are stored in browser `localStorage` and are never transmitted. There is no account, no login, no analytics, no tracking, and no server that could receive a farmer record. Opening the app contacts no third party except the Open-Meteo forecast, which receives the district's coordinates and nothing about the farmer; the typefaces are served from the app itself.

**Voice is the one stated exception.** A question asked by voice is recognised by the browser's own speech service, which in Chrome sends the audio to Google. The Ask screen says so beside the microphone, and a typed question never leaves the phone.

The federation design is explicit about this boundary: **models and methods cross state borders; farmer records never do.** A disease pattern learned in one state improves detection in another without a single personal record moving.

API credentials never enter the client bundle. The data scripts read the one key they need from a git-ignored `.env.local` on a developer machine, or from a repository secret in CI, and never log it.

The deployment sends a strict Content-Security-Policy that allows only the app itself and the Open-Meteo forecast, and forbids the page from being framed by another site. It also sends `X-Content-Type-Options: nosniff`, a strict referrer policy and a permissions policy. `npm run preview` sends the same headers, so a change that would break under them fails locally first.

### 8. Standards and best practices

- Open data formats throughout — JSON, NetCDF, CSV
- Established statistical methods, named and cited: Theil–Sen, Mann–Kendall
- The onset days behind every trend are **reproducible from raw rainfall**: `scripts/detect_onsets.py --check` regenerates them from the IMD grid and confirms the committed file byte for byte, and CI does this on every push along with lint, tests and a build.
- Those methods are **independently verified**, not merely named. `scripts/verify_stats.py` checks the shipped
  implementations against scipy, pymannkendall and a permutation test, and reproduces every district from the
  raw onsets. A reviewer does not have to take the significance claim on trust.
- Trilingual interface (Marathi, Hindi, English) in Unicode Devanagari
- Accessible by construction: WCAG-AA-oriented contrast, 16 px minimum body text, no hairline weights, `prefers-reduced-motion` respected
- Installable PWA with a service worker: the app shell, precomputed data and satellite frames are precached, so it opens and answers offline on 2G. The live forecast uses network-first with a cached fallback and refreshes every 15 minutes while the app is open; the app re-fetches the latest prices every 30 minutes, so an installed copy stays current without an update.

### 9. Do no harm by design

This is where most agricultural advisory tools fail, so it is stated in detail.

**The app refuses to assert what it cannot measure.** Onset trends were tested for statistical significance in all 36 districts. Only two clear p < 0.05. For the other 34, the interface says so in the farmer's own language —

> *"Across 41 years, Latur shows no measurable shift in the monsoon date. We will not pretend otherwise."*

— and renders the trend line dashed and grey rather than confident. A false sowing-date correction would cause exactly the crop failure this tool exists to prevent.

**Unsourced figures are labelled as such, in the interface.** Per-acre income figures are placeholders pending CACP cost-of-cultivation data, and carry a visible `नमुना आकडे` / *sample figures* badge everywhere they appear. Real mandi prices are shown separately and are not mixed with estimates.

**Data provenance is shown to the user,** not buried in a repository. The evidence screen exposes the source dataset, the onset rule, the trend method, and the live p-value for the district being viewed.

**We record our own wrong turns.** The project initially used ERA5 reanalysis and obtained per-district results that did not hold up against the literature on reanalysis precipitation trends over India. We switched to IMD ground-station data and documented why in the README. ERA5 remains the live forecast; it is not the evidence base.

**Questions are answered by retrieval, not generation.** The question screen composes every answer from data the app already holds — IMD onset, live forecast, Agmarknet prices, rotation rules — and never from a language model. A model that hallucinates a sowing date would cause exactly the germination failure this project exists to prevent, and a farmer cannot audit a fluent wrong answer. When no intent matches, it says it did not understand rather than guessing.

**Soil figures are the district's odds, and say so.** Soil Health Card results are published per district as counts of tested fields, not per farmer. The app shows "74% of fields tested in Nashik are low in nitrogen" and states on the same screen that this is not a reading of the farmer's field — then tells him where to get one, free. The rotation engine still reports a *relative* nitrogen balance rather than inventing a starting organic-carbon percentage for a field nobody tested.

**Selling advice is a record, not a forecast.** *When to sell* shows what waiting has paid in each of the last 11 years in that district, and in how many of them it paid at all. The one assumed number — a 1%-a-month cost of holding — is printed next to the advice. Onion carries an extra warning that stored onion loses weight, which the price record cannot see.

**Rupee figures name their source on the card.** The cost of sowing on the old date cites the field trial it is priced from and shows its four measured yields.

## What is not yet a DPG-grade claim

Stated plainly, because a public good that hides its gaps is not one:

- **Per-acre yield and cost** are placeholders. Income figures are badged as samples until sourced from CACP tables.
- **Crop water requirements and sowing windows** are agronomically plausible but not yet cited to a state package of practices. The climate-resilience score is built on those same rules of thumb, so it inherits the caveat; it is scored only where the monsoon record can speak to the crop, and summer crops grown on well water return no score at all rather than a misleading one.
- **Prices cover all 36 districts**, fetched state-wide each run. Districts absent from a day's data had no arrivals, which the interface says; a crop with no local arrivals falls back to the state median, labelled as such.
- **Soil is district-level.** The Soil Health Card system is integrated for 34 districts, but as shares of tested fields; a farmer's own card number is not read. Field-level lookup is the next step and would need the farmer's consent.
- **The late-sowing loss rate comes from one trial.** One season (2014) at Akola, applied to other districts. It is conservative — a low-yield year — but it is not a Nashik measurement.
- **Crop stage is estimated** from the corrected sowing window and the crop's duration, not observed; field warnings key off that estimate.
- **Only the India node is computed.** The federation roster on `/policy` names the onset question each other nation's archive would be asked, and marks all four as not computed. No figure is shown for any of them.
- **The disease diagnostic is built and shipped, and covers one crop of nine.** PlantVillage — the only free labelled leaf dataset available to us — carries 38 classes across 14 plants, and the only overlap with a RITU crop that has any *disease* class is maize. Soybean appears solely as `healthy`; bajra, cotton, wheat, gram, onion, groundnut and moong are absent. The app diagnoses maize and refuses the rest by name. Widening it is a data problem — field-collected Indian images for those crops — not a modelling one.
- **Measured, not asserted.** Held-out accuracy is 0.8667, and the per-class recall behind it is uneven: rust 0.98 and
  healthy 1.00, but gray leaf spot 0.74 and northern leaf blight 0.71, which are confused with each other in both
  directions. The full confusion matrix ships beside the weights in `public/model/maize/metrics.json`, and the
  interface warns when the answer is one of the two weak classes.
- **It is trained on laboratory photographs.** PlantVillage images are single detached leaves on plain backgrounds. Held-out accuracy on such a split is an upper bound and overstates field performance, where soil, shadow and overlapping leaves are the norm. The interface says so on the diagnosis screen, not only here, and the model declines to answer below 60% confidence rather than committing a farmer to a spray.
- **Disease loss fractions and spray costs are not sourced.** They are `SAMPLE_` prefixed in the code and badged in the interface. The disease names, symptoms and treatment classes are ordinary maize agronomy.
